HEAD FIRST REDIS + SOCKET.IO

Understand Realtime Here Like You Implemented It

This is not a generic Redis or Socket.IO tutorial. It is a deep walkthrough of note-canva-backend: exact keys, exact handler flow, exact fan-out path, and current tradeoffs.

Goal: if someone asks "how does realtime sync work in your backend?" you can answer at key-level and function-level, not just concept-level.

Chapter 0: Big Picture First

One-line architecture summary

Redis is the live board state + coordination memory, Socket.IO/WS are transport layers, SQL is durable store, and workers flush/cleanup Redis over time.

Realtime mental modelpseudo
client sends mutation
  -> transport handler validates payload + permission
  -> mutation processor computes canonical change
  -> boardStateService writes change to Redis (elements/seq/dirty/change-log)
  -> publish ELEMENTS_CHANGED on board:{id}:mutations
  -> each realtime instance sends change to its local clients

later (worker):
  -> persist dirty boards from Redis to SQL
  -> cleanup stale Redis boards safely

Why Redis exists in this app

  • Collaboration needs very fast reads/writes for board elements.
  • Reconnect needs short-term history (board:{id}:changes) for CATCH_UP.
  • Presence needs short-lived session/client tracking (clients, viewer_sessions).
  • Cross-instance fan-out needs pub/sub channels (board:{id}:mutations).
Important: Redis is live canonical state between flushes, but SQL remains durability anchor. This is why persistence workers exist.

Atomicity and pipelines (why they matter)

Collaboration state can break if related writes split across multiple round trips. This codebase uses pipeline() and Lua eval where consistency matters.

Atomic-ish grouped update in applyChangeSet()TypeScript
const pipeline = redis.pipeline()

pipeline.hset(board:{id}:elements, ...)
pipeline.rpush(board:{id}:changes, JSON.stringify(change))
pipeline.ltrim(board:{id}:changes, -CHANGE_LOG_MAX_LENGTH, -1)
pipeline.sadd(boards:dirty, boardId)
pipeline.incr(board:{id}:dirty_epoch)
...
await pipeline.exec()

Persistence clear step uses Lua to avoid race between "what was flushed" and "new writes happened while flushing" by checking dirty_epoch first.

Epoch guard ideapseudo
if current_dirty_epoch != snapshot_dirty_epoch:
  do not clear dirty markers
  // because new writes arrived during flush
else:
  clear dirty markers safely

Pub/Sub and fan-out basics (the missing explanation)

Fan-out means "one logical change is delivered to many clients". In distributed realtime, those clients may be connected to different server instances.

  • Publisher: server that applied canonical change publishes to board:{id}:mutations.
  • Subscribers: all realtime instances that care about that board receive message.
  • Local rebroadcast: each subscriber sends message to its own local sockets in that board room.
Key point: Pub/Sub itself does not store history. If a subscriber is offline, it misses messages. Reconnect correctness comes from snapshot/change-log, not pub/sub replay.

Board lifecycle in Redis

Lifecyclepseudo
join board:
  loadBoard(boardId) -> seed Redis from SQL if not loaded
  track client + viewer session

edit board:
  applyChangeSet -> update elements/seq/change-log/dirty markers
  publish board:{id}:mutations

steady state:
  clients reconnect via CATCH_UP if change-log has gap coverage
  fallback SNAPSHOT otherwise

idle board:
  persistBoard(boardId)
  flushBoard(boardId)
  remove transient state eventually

Workers that keep Redis healthy

  • Persistence worker (boardPersistenceService): flushes dirty boards to SQL continuously.
  • Cleanup worker (redisCleanupService): finds inactive boards, persists then flushes, and deletes stale transient keys.
Why cleanup is careful: it checks global client/viewer counts before flushing, to avoid dropping hot board state while users are connected.

Chapter 4: Fan-out Demystified (Your Exact Confusion)

What fan-out means in one sentence

Fan-out is: one canonical change in one server instance becomes many outbound messages to clients across all instances that host that board.

Two fan-out layers you must separate

LayerMechanismScope
Local fan-outsocket.to(boardId).emit(...) or room manager broadcastOnly clients connected to same process
Cross-node fan-outpubRedis.publish + per-node subscriber + local rebroadcastClients across multiple processes/pods

Presence across multiple nodes (ELI5)

Think of each realtime node as a classroom. Presence events are currently announced with a classroom speaker (socket.to(boardId).emit). Students in that classroom hear it, students in other classrooms do not.

ActionTodayWhy this can break
User moves cursor on Node ANode A emits presence to its local roomUsers on Node B may not receive cursor updates
User joins board on Node BNode B emits join locallyNode A may show stale participant list
Global counts in Redisclients/viewer_sessions do updateCounts are global, but real-time UI events are still local-only unless bridged
ELI5 presence split-brainpseudo
Node A room has Alice
Node B room has Bob

Alice moves mouse:
  Node A tells only Node A clients
Bob may not see Alice cursor

Bob types:
  Node B tells only Node B clients
Alice may not see Bob typing indicator
Important distinction: Redis presence keys can say \"2 viewers active\", but UI can still show incomplete live cursors if event broadcast is not cross-node.

How multi-node Redis works for this architecture

Today this backend creates separate Redis connections (redis, pubRedis, jobsRedis) but they can still point to one Redis server URL. \"Multiple Redis nodes\" usually means one of these topologies:

TopologyHow it behavesImpact here
Single RedisOne primary handles all reads/writes/pubsubSimplest; realtime + jobs share one failure domain
Primary + replica(s) + SentinelAutomatic failover to new primaryBetter HA; short failover window can drop pub/sub messages
Redis Cluster (sharded)Keys distributed by hash slotGreat scale for keyspace; pub/sub semantics differ by mode and require cluster-aware client setup

For collaborative fan-out, treat pub/sub as transient. If Redis node failover happens, missed pub/sub events must be recovered by reconnect CATCH_UP/SNAPSHOT, not by expecting pub/sub replay.

Multi-node Redis mental modelpseudo
realtime server receives mutation
  write canonical state keys (elements/seq/dirty)
  publish to mutation channel

if Redis failover during publish:
  some subscribers may miss message
  correctness still comes from:
    sequence + changes log -> CATCH_UP
    else full SNAPSHOT

Current project truth (important)

From current code:

  • Socket.IO mutation handlers publish to Redis channel (src/socketio/server.ts).
  • Raw WS stack has explicit Redis subscriber/rebroadcast (src/ws/pubsub.ts + room manager).
  • Socket.IO stack currently has no equivalent Redis subscribe + rebroadcast path and no @socket.io/redis-adapter.
ScenarioWorks now?Reason
Single realtime instanceYesLocal room emits are enough
Multi-instance raw WS clientsYes (for channels subscribed by WS room manager)subRedis.on('message') rebroadcast exists
Multi-instance Socket.IO presence/tick room eventsNot guaranteedNo Socket.IO adapter/subscriber bridge
Interpretation: your previous fan-out confusion was valid. Current behavior is mixed by transport path, so docs must be explicit about what is local-only versus distributed.

Production-grade fix options

  1. Add @socket.io/redis-adapter so Socket.IO rooms/events replicate across nodes.
  2. Or enforce sticky routing per board/session (all board sockets stay on one node).
  3. Keep pub/sub payload contract centralized so WS and Socket.IO emit compatible server events.

ELI5 decision: adapter vs sticky

Sticky routingKeep same board users in one classroomSimpler events, but balancing and failover routing become critical

Project code examples explained

Example A: Why withBoardMutationLock exists

Without per-board lock, two concurrent mutation batches could compute change sets from stale context and scramble sequence/order. The lock serializes mutation application per board.

Example B: Why getSyncWriteMode() switches solo/collab

In solo mode, code can persist aggressively and may skip some change-log retention pressure. In collab mode, change-log tracking is essential for reconnect deltas.

Write mode decisionfrom presence-domain.ts
if collab_mode_until is still future:
  mode = collab
else if active clients/viewers >= 2:
  extend collab_mode_until
  mode = collab
else:
  mode = solo

Example C: Why reconnect can fail over to snapshot

sendInitialState() asks for getChangesAfter(lastSequence). If change-log no longer has a complete contiguous range, server sends full snapshot for correctness.

This is the intended safety rule: never send partial delta if there is a gap; snapshot is slower but correct.

Mutation combination and SQL upserts (full pipeline)

Mutation combining happens in two places:

  1. Transport-side batch input (mutation:batch) groups many mutation operations per board into one processor call.
  2. Persistence-side incremental flush groups many changed element IDs into one SQL transaction with delete + upsert.
Detailed data pathpseudo
client sends [m1, m2, m3] for same board
  -> processBatch() under one board lock
  -> each mutation:
       tryMarkSeen(mutationId) // dedupe
       toChangeSet(operation)
       applyChangeSet()
         - increment sequence
         - write element hash upserts/deletes
         - append change-log (collab mode)
         - add dirty markers

later persistence worker:
  read dirty_element_ids + deleted_element_ids
  hmget current element JSON for dirty IDs
  db transaction:
    delete removed rows
    insert ... onConflictDoUpdate for upserts
    touch board updated_at
  if dirty_epoch unchanged -> clear dirty markers
StepWhere in codeWhy it is optimized
Batch by boardsrc/mutations/processor.ts byBoard mapReduces lock churn and repeated context reads
Targeted readsgetElementsByIds() when enabledAvoids full hgetall for large boards
Incremental persistencepersistBoardIncremental()Flushes only changed/deleted IDs, not full snapshot
SQL upsertonConflictDoUpdate in persistence domainOne statement handles insert-or-update rows efficiently

Mini batching and other optimization ideas

You already have mini-batching in raw WS handler (MUTATION_BATCH_WINDOW_MS=12, max size 25) and targeted reads in processor. For higher load, add these safely:

  1. Socket.IO mini-batch window: queue per-socket mutation events for 5-15ms before processBatch (same pattern as WS).
  2. Cross-socket board coalescing: short board-level queue to merge bursts from many clients into one board lock acquisition.
  3. Flush chunking: for very large dirty sets, split hmget/insert values into bounded chunks (e.g., 500-2000 IDs) to avoid oversized SQL packets.
  4. Adaptive batch windows: widen window when queue depth is high, shrink when latency SLA is threatened.
  5. Hot-key protection: cap board-level mutation rate and surface backpressure metrics before Redis CPU saturates.
Rule of thumb: batch for throughput, but keep end-to-end user-perceived mutation latency low (usually under 50-100ms for collaborative editing actions).

Interview-grade self-checks

Why can reconnect choose snapshot even if client has lastSequence?

Because Redis change-log is capped and short-lived; if contiguous delta range is missing, only snapshot preserves correctness.

What exactly prevents duplicate mutation apply?

tryMarkSeen(board:{id}:seen:{mutationId}) with TTL and NX semantics in mutation processor path.

What makes fan-out cross-node, not just local?

Publisher + Redis channel + subscriber on each node + local rebroadcast. Missing any one part means partial fan-out.

Chapter 7: Multi-node Failure Scenarios

What can fail in distributed realtime

FailureSymptomRecovery path
Realtime pod crashSome clients disconnect; others stay connected on other podsReconnect to healthy pod, then CATCH_UP/SNAPSHOT
Redis primary failoverShort publish/write errors, possible missed pub/sub emissionsRetry writes, reconnect clients, recover via sequence/change-log/snapshot
Network partition between pods and RedisDivergent local state events until reconnectResubscribe, rehydrate board state, rely on canonical Redis/SQL after healing
Worker outageRedis memory grows, SQL lag increasesRestart workers; persist dirty boards backlog

Multi-node verification drill (practical)

Failure drill checklistops
1) Run >=2 realtime instances and shared Redis
2) Open same board from clients pinned to different instances
3) Generate steady mutation traffic
4) Kill one realtime instance
5) Confirm reconnect behavior:
   - recent disconnect -> CATCH_UP
   - long gap -> SNAPSHOT
6) Trigger Redis restart/failover
7) Confirm:
   - app recovers without manual cache clear
   - sequence monotonicity preserved
   - no permanent board divergence

Hardening checklist for multi-node prod

  1. Add explicit Socket.IO cross-node strategy: Redis adapter or strict sticky routing.
  2. Use Redis HA (Sentinel/managed failover) and test failover quarterly.
  3. Track metrics: reconnect rate, snapshot fallback rate, Redis publish failures, flush lag, dirty set size.
  4. Set alerting on sustained growth of boards:dirty and persistence backlog age.
  5. Document runbook for Redis failover and realtime pod rollouts.
