Minimal Zod + Express pattern (this project style)

Pattern used in routes like src/routes/workspaces.ts and src/routes/boards/shared.ts:

Minimal validated endpointTypeScript
const paramsSchema = z.object({ id: z.string().trim().min(1) })
const bodySchema = z.object({ name: z.string().trim().min(1) })

router.patch('/boards/:id', async (req, res) => {
  const params = parseWithSchema(paramsSchema, req.params)
  if (!params.success) return sendBadRequest(res, params.error.error)

  const body = parseWithSchema(bodySchema, req.body)
  if (!body.success) return sendBadRequest(res, body.error.error)

  const updated = await boardService.renameBoard(params.data.id, body.data.name)
  return res.json(updated)
})

Important for your AGENTS rule: validate req.params, req.query, and req.body before business logic.

Task A Walkthrough: Add optional board maxDimensions

Goal: backend stores camera bounds so frontend can clamp camera to [-width/2, width/2] and [-height/2, height/2].

Task A first-pass pseudocodepseudo
when creating/updating board:
  accept optional maxDimensions { width, height }
  validate both positive ints
  persist on boards table
  return in all board read DTOs

frontend camera:
  if maxDimensions exists:
    clamp center to +/- width/2 and +/- height/2
  else:
    keep current free camera

Step 1: Data model

  • Create a migration: add nullable columns on boards: max_width, max_height (integers) or one jsonb. Prefer two ints for easy filtering/indexing.
  • Update src/db/schema.ts boards table to include these columns.

Step 2: API schemas

  • In src/openapi/schemas.ts, extend createBoardBodySchema to include optional maxDimensions object.
  • Validate positive safe limits:
Recommended Zod shapeTypeScript
const maxDimensionsSchema = z.object({
  width: z.number().int().positive().max(100000),
  height: z.number().int().positive().max(100000),
})

export const createBoardBodySchema = z.object({
  name: z.string().trim().min(1),
  maxDimensions: maxDimensionsSchema.optional(),
})

Step 3: Route + service plumbing

  • src/routes/boards/management.routes.ts: POST /workspaces/:wid/boards and PATCH /boards/:id should pass optional dimensions.
  • src/services/board.service.ts: update create/rename/update methods and returned board DTO.
  • GET /boards and GET /boards/:id should include this field so frontend can apply clamp logic immediately.

Step 4: Tests

  • Add route tests: accepts valid dimensions, rejects negative/zero with 400, accepts missing dimensions.
  • Run: just build then just test.

Frontend contract

Frontend reads board.maxDimensions. If absent, camera remains unbounded. If present, clamp camera center to half-range.

  • Migration: update elements.type constraint to include AI_NODE (pattern already exists in drizzle/0008_table_element_kind.sql).
  • Node payload lives in element data, example fields:

Step 3: Connector API (Zod-first)

  • Add routes under /workspaces/:wid/ai/connectors: create/list/update/delete.
  • Validate params/query/body with Zod before service calls.
  • Reuse workspace role checks from existing workspace/board access model.

Step 4: Execution model for node runs

  • New service: ai-node.service.ts to execute graph steps using connector credentials.
  • Run async via jobs Redis (same pattern as preview jobs) for reliability/retries.
  • Persist run metadata in new table: ai_node_runs.

Step 5: Realtime streaming design

Use Socket.IO events for token streaming to active board viewers:

  • ai:run:start (nodeId, runId)
  • ai:run:chunk (token/text delta)
  • ai:run:done (final output)
  • ai:run:error

Then write final node output back as canonical board element update through mutation processor, so SQL/Redis stay source-of-truth aligned.

Chapter 1 Interview Questions

Why validate params/query/body separately with Zod?

Because each surface has different trust and error semantics. It keeps failures explicit and prevents hidden coercions reaching services.

Where should board shape fields like maxDimensions live?

In board domain (schema + board service + board routes), not mutation payloads, because they are board-level metadata, not per-element collaborative state.

Chapter 2: WebSocket / Socket.IO / Redis / Fanout

High-level overview first (pseudocode)

Socket.IO + Redis flowpseudo
on socket connect:
  wait for board:join
  authorize board access
  load board state from Redis/SQL
  add participant to room
  emit board snapshot

on mutation:batch:
  validate payload
  process canonical changes via mutationProcessor
  ack sender
  broadcast mutation to local room
  publish ELEMENTS_CHANGED to Redis channel

on other realtime node receiving Redis message:
  fanout to its local clients in same board room

on reconnect:
  if sequence is still in Redis change-log -> send CATCH_UP
  else -> send full SNAPSHOT

Redis responsibilities in realtime

Key / channelPurpose
board:{id}:elementsCurrent canonical board element set in Redis

What “fanout” means here

One client sends mutation. Server applies canonical change once. Then server publishes to Redis channel. All realtime instances subscribed to that board receive and rebroadcast to their local sockets in that board room.

SVG · Reconnect decision (CATCH_UP vs SNAPSHOT)

Scaling plan (important)

  • Good now: canonical element changes are cross-instance via Redis pub/sub.
  • Gap now: Socket.IO room presence events are local emits; without sticky routing or Redis adapter, presence/user-join can fragment across nodes.
  • For scale: either enforce sticky sessions per board, or add @socket.io/redis-adapter and broadcast presence through adapter/pubsub path.
  • Keep realtime and API split by host as already documented in docs/k8s-migration-baseline.md.
Scale checklistops
1) Keep APP_ROLE split in production (api/realtime/worker)
2) Use Redis with persistence (AOF/RDB) and monitor memory/evictions
3) Add socket.io redis adapter OR sticky board routing
4) Monitor: reconnect rate, catch-up fallback-to-snapshot rate, flush latency
5) Backpressure: cap mutation batch and message size (already partially done)

Chapter 2 Interview Questions

Why keep Redis change log short-lived instead of permanent?

Cheap reconnects for recent disconnects, without long-term write amplification. SQL remains compact canonical state; history is not source-of-truth.

When should reconnect send CATCH_UP vs SNAPSHOT?

CATCH_UP when requested sequence is still covered by Redis changes; otherwise snapshot for correctness.

Chapter 3: Stripe Integration (Current + Next)

High-level overview first (pseudocode)

Billing flowpseudo
request checkout(plan):
  ensure stripe configured
  resolve/create customer
  create checkout session
  return checkout URL

receive webhook(event):
  verify stripe signature
  dedupe event id in DB
  update customer/subscription records
  recompute effective plan for profile endpoint

Concrete pass

Billing is toggled by config flags. If Stripe keys are missing, non-prod falls back to dev plan behavior.

Current data model

  • billing_customer_links
  • billing_subscriptions
  • billing_webhook_events (idempotency by Stripe event id)

Checkout + webhook flow

  1. Frontend calls POST /billing/checkout with plan.
  2. Backend creates Stripe Checkout Session in billing.service.ts.
  3. Stripe sends webhook to POST /billing/webhook.
  4. Backend verifies signature and dedupes event before updating subscription records.

Production hardening checklist

  • Enforce strict webhook secret and rotate regularly.
  • Keep webhook handler idempotent (already done using onConflictDoNothing by event id).
  • Track async webhook failures and retry alerting.
  • Store entitlement cache in DB (plan/limits) and avoid runtime calls to Stripe on hot paths.
  • If moving to Better Auth org billing, map org id in metadata consistently.

Chapter 3 Interview Questions

Why can’t checkout completion alone define entitlements?

Because subscription lifecycle changes later (trial end, pause, cancel, payment failure). Webhooks are the long-term truth stream.

How do you make webhook processing safe on retries?

Deduplicate by Stripe event id in DB before processing side effects. If insert conflicts, treat as already-processed.

Chapter 4 Interview Questions

What is your default sequence for adding a new backend feature safely?

Migration/schema first, strict Zod validation on all inputs, service-layer logic, tests, then realtime side-effects and OpenAPI updates.

How do you debug a mismatch between REST data and realtime board state?

Trace mutation processor and boardStateService first, inspect Redis keys/sequence/change-log, then verify SQL flush timing and route payloads.
